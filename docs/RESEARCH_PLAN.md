# RSAShield — Research & Implementation Plan

**Project title:** Auditing Substation RSA Keys Using a Multi-Signal Key-Quality Framework (with a bounded role for Lenstra's Elliptic Curve Method)

**Status:** Planning / pre-implementation. GitHub repo `333shubh/RSAshield` is currently empty; local working copy contains only `image.png` (a screenshot of an intended prototype's passing test table). This document is the gap analysis and plan required before any code is written.

**Scope & ethics (binding on all work):** Synthetic keys and explicitly-authorised datasets only. The prototype stays offline and is never connected to live OT/SCADA networks. No probing, scanning, authenticating to, or modifying of real substation equipment. Private factors and ground-truth labels live only inside the test harness, never in operator-facing reports.

---

## 1. What this project is really about (and one correction that reframes it)

RSAShield is a **defensive RSA key-quality auditor**: given RSA *public* keys (from device inventories, certificate exports, config backups — all obtained with permission), it flags keys that were likely produced by broken or entropy-starved key generation, so operators can prioritise replacement. This is the same class of work as Heninger et al.'s *Mining Your Ps and Qs*, the ROCA disclosure, and tools like `badkeys`.

### The correction at the centre of the plan

The original one-line "novelty" claim was:

> *Uses Lenstra's ECM to identify weak RSA moduli (n = p·q) generated by entropy-starved grid microcontrollers.*

This is **cryptographically inaccurate as stated**, and an examiner will catch it. Entropy-starved key generation overwhelmingly produces three failure modes, and **ECM is the right tool for none of them**:

| Failure mode from weak entropy | What it looks like | Detector that actually finds it |
|---|---|---|
| Two devices draw a **shared prime** | `n₁ = p·q₁`, `n₂ = p·q₂` | **Batch GCD** (`gcd(n₁,n₂)=p`) — *not* ECM |
| One device draws **primes too close** | `p ≈ q`, so `n ≈ (√n)²` | **Fermat** factorization — *not* ECM |
| Structured primes (e.g. Infineon/ROCA) | `p = k·M + (65537ᵃ mod M)` | **Fingerprint + Coppersmith** — *not* ECM |

**Why ECM does not fit the headline claim.** Lenstra's ECM running time depends on the size of the *smallest* prime factor of `n`, not on the size of `n`. It is excellent at pulling out *small* factors (tens of digits) and *unbalanced* factors (`p` much smaller than `q`). But a weak-entropy key is usually still a **balanced semiprime** — `p` and `q` each ~half the bits of `n` — and against a balanced 1024/2048-bit semiprime, ECM is as infeasible as the General Number Field Sieve. So ECM cannot be the primary engine for the stated problem.

**The honest reframing (this becomes the project's thesis).** RSAShield is a **multi-signal** auditor. ECM is retained as **one bounded detector covering one specific failure mode** — moduli with a small or unbalanced factor (implementation bugs, truncated primes, off-by-one prime sizing, mixed-size prime pairs) — run under a strict time/curve budget. A failed ECM attempt proves nothing; a successful one is sufficient but not necessary evidence of a defect. The intellectual contribution is the framework, the evaluation, and the domain application — **not** "ECM detects weak keys."

This correction is defensible, well-sourced (§8), and is itself the strongest thing to foreground in the report.

## 2. Cryptographic background (for correctness, §correctness of the brief)

**RSA key structure.** Public key `(n, e)`, `n = p·q` with `p, q` large primes (~`k/2` bits each for a `k`-bit modulus). Private exponent `d ≡ e⁻¹ (mod λ(n))`, `λ(n) = lcm(p−1, q−1)`. Security rests on the hardness of factoring `n` and of the RSA problem. Typical `e = 65537`.

**Where key generation goes wrong under weak entropy.**
- *Insufficient seeding at boot* ("boot-time entropy hole" in headless/embedded devices) → RNG output is predictable or repeated across devices/power cycles → **shared primes** between distinct devices.
- *Shortcut prime generation* (e.g. `q` drawn adjacent to `p`, or both from a narrow pool) → **close primes**.
- *Vendor library structure* (ROCA) → primes from a restricted algebraic form, detectable by a cheap fingerprint even without factoring.
- *Implementation bugs* → tiny factors, unbalanced prime sizes, non-standard exponents, `d` chosen small for speed (Wiener).

**The four complementary detectors.**
1. **Metadata / structural checks** — modulus bit length vs policy, `e` sanity (non-65537, even, 1), `n` parity, `n` being a perfect power, byte-level entropy / monobit / run statistics on the modulus. Cheap, high-recall screens; weak on their own (advisory, not proof).
2. **Small-factor trial division + bounded ECM** — recovers small/unbalanced factors. Trial division handles the truly tiny; **ECM** extends reach to medium (unbalanced) factors under budget.
3. **Fermat factorization** — recovers `p, q` when `|p − q|` is small; iterate `a = ⌈√n⌉, ⌈√n⌉+1, …` testing `a² − n` for a perfect square. Bound the iteration count.
4. **Batch GCD across the corpus** — finds shared primes *between* keys. Pairwise `gcd` is `O(N²)` big-integer GCDs; Bernstein's **product-tree / remainder-tree** batch GCD computes each key's GCD against the product of all others in ~`O(N log²N)` and is the standard scalable method.

Plus **Wiener's attack** screen (continued-fraction convergents of `e/n`) for dangerously small `d`, and an **optional ROCA fingerprint** (fast discrete-log test) for Infineon-style structure.

**Lenstra's ECM, precisely.** Pick a random elliptic curve `E` over `ℤ/nℤ` and a point `P`. Compute `[k]P` for a highly composite `k` (product of prime powers up to bound `B₁`; optional stage-2 to `B₂`). The group law requires a modular inverse; when that inverse fails because the intermediate value shares a factor with `n` — which happens when the curve's order mod some prime factor `pᵢ` is `B`-smooth — `gcd(value, n)` reveals `pᵢ`. Expected cost grows subexponentially in the size of the *smallest* factor, so ECM is budgeted by `(B₁, B₂, #curves, wall-clock)`. **Distinction the brief asks for:** ECM finds *factors that happen to be small or unbalanced*; it does **not** detect shared-prime, close-prime, structured-prime, or small-`d` defects — those are other detectors' jobs. ECM finding nothing ≠ key is healthy.

**Adjacent / prior work that overlaps (so we don't reinvent or over-claim):**
- **`3BK/RSAPubKeyHealth`** (Rust) — implements *almost this exact check list*: size policy, exponent sanity, Shannon entropy, monobit, runs, repeated/sparse bytes, small-factor, Fermat, shared-factor vs a supplied corpus, Wiener, SPKI SHA-256 fingerprint, compliance mapping. **It has no ECM, no SCADA framing, and no reproducible benchmark.** (Very likely your own earlier work — it maps the gaps precisely.)
- **`badkeys`** (Hanno Böck) — library/site checking keys against known vulns: Debian OpenSSL, common factors, ROCA, Fermat.
- **`cryptosense/keytester`**, **`factorable.net`** tooling, **Keyfactor's 75M-certificate IoT study** — internet-scale shared-factor / weak-key detection.

**The concrete gaps RSAShield can fill (these become the contributions):**

| # | Gap in existing tools & literature | What RSAShield adds |
|---|---|---|
| G1 | Tools detect; almost none ship a **controlled benchmark with ground truth**. Literature evaluates on internet scans (no labels, no private factors). | A reproducible, **fault-injected, labelled** benchmark with known `p,q` and defect tags, and per-detector precision/recall/runtime/memory. |
| G2 | ECM's role is usually hand-waved or omitted. | A **bounded-ECM budget policy** with a measured **marginal-yield study** (when ECM is worth it vs never). |
| G3 | No tool frames findings for **ICS/substation** constraints. | A threat + remediation model for long-lived, hard-to-rotate grid keys, mapped to **IEC 62351 / NERC CIP**. |
| G4 | Binary "weak/not" output; some tools wrongly imply "secure". | A **calibrated multi-signal risk score** with per-signal confidence that **never labels a key secure** — only "no defect found under budget B". |
| G5 | No explicit mapping from a positive signal to *which* generation defect caused it. | A **detector → failure-mode attribution taxonomy** driving remediation advice. |

## 4. Novel research contribution (stated honestly)

**Not novel (do not claim it is):** the individual algorithms (ECM, batch GCD, Fermat, Wiener) are textbook; *combining* them is already done by `badkeys` and `RSAPubKeyHealth`. A combination of established algorithms is not, by itself, a research contribution.

**Genuinely novel at final-year-project level** (systematisation + evaluation + domain application, not a cryptographic breakthrough):

- **N1 — A reproducible labelled benchmark for weak RSA key generation.** Controlled fault injection modelling grid-microcontroller failure modes, with ground-truth factors and defect labels held in the harness, enabling true precision/recall/false-positive measurement that scan-based studies cannot produce. *This is the primary contribution.*
- **N2 — A calibrated, uncertainty-aware risk model** that fuses weak signals, reports per-signal confidence, and is disciplined never to assert security — only bounded non-detection. Addresses a real, recurring misuse of such tools.
- **N3 — A bounded-ECM budgeting policy with a cost/yield model** for the offline-fleet setting: what `(B₁,B₂,curves,time)` is worth spending per key given fleet size `N` and the marginal detection it buys over GCD+Fermat.
- **N4 — Domain contextualisation for substation/SCADA**: attribution of findings to operational risk and remediation under IEC 62351 / NERC CIP constraints.

**Limitations to state up front:** no detector proves a key secure; ECM contributes only on small/unbalanced factors; synthetic benchmarks model but do not equal field distributions; batch GCD only finds *shared* primes present *within the audited corpus*.

## 5. Research questions

- **RQ1 (complementarity).** On a controlled corpus, what are each detector's precision/recall, and where do they overlap vs cover disjoint failure modes? *Hypothesis: GCD, Fermat, ECM, Wiener are largely disjoint; metadata checks are high-recall/low-precision screens.*
- **RQ2 (ECM budget).** For unbalanced/small-factor keys at 1024/2048 bits, what bounded `(B₁,B₂,#curves,time)` yields meaningful marginal detection, and for which key classes is ECM *never* worth running vs GCD/Fermat?
- **RQ3 (fusion).** Can a calibrated multi-signal score rank key risk better than any single detector at a fixed false-positive budget, without ever emitting a "secure" label?
- **RQ4 (scaling).** How do detection yield and cost scale with modulus size and fleet size `N` (batch-GCD tree vs naïve pairwise)?

## 6. Defensible architecture (modular, offline)

```
                      ┌──────────────────────────────────────────────┐
  authorised input →  │ 1. Input validation & intake                 │
  (PEM/DER/SPKI,      │    size caps, encoding checks, quarantine dir │
   X.509, SSH pub)    └──────────────────┬───────────────────────────┘
                                         ▼
                      ┌──────────────────────────────────────────────┐
                      │ 2. Parser / normaliser → (n, e, source_meta)  │
                      └──────────────────┬───────────────────────────┘
                                         ▼
     ┌───────────────────────────────────────────────────────────────────────┐
     │ 3. Detector pipeline (each emits a typed Signal + evidence + cost)      │
     │   3a metadata/structural   3b small-factor+bounded ECM                  │
     │   3c Fermat (close primes) 3d Wiener (small d)                          │
     │   3e batch GCD across corpus   3f (optional) ROCA fingerprint           │
     └──────────────────┬────────────────────────────────────────────────────┘
                        ▼
     ┌─────────────────────────────┐     ┌──────────────────────────────────┐
     │ 4. Evidence aggregator      │     │  Benchmark harness (separate)     │
     │    → failure-mode attribution│    │  key-gen + fault injection +      │
     │ 5. Calibrated risk scorer   │     │  ground-truth store + evaluator   │
     └──────────────┬──────────────┘     └──────────────────────────────────┘
                    ▼
     ┌───────────────────────────────────────────────────────────────────────┐
     │ 6. Report generator                                                     │
     │    • Operator report: finding + failure mode + remediation (NO p/q)     │
     │    • Forensic/eval report: harness-only, may include recovered factors  │
     └───────────────────────────────────────────────────────────────────────┘
```

**Design rules.**
- Every detector returns a uniform `Signal{ type, verdict, confidence, evidence, cost_ms, budget_spent }`; the scorer consumes signals, never raw private data.
- **Redaction is structural:** recovered factors are written only to the harness ground-truth store. The operator report layer has no code path that can print `p`/`q`.
- Classifications are `FACTOR_RECOVERED` / `DEFECT_SUSPECTED` / `NO_DEFECT_FOUND(budget=B)`. There is **no `SECURE` label**.
- Fully offline; corpus comes from files. No network client to any OT system exists in the codebase.

**Suggested stack:** Python 3.11+, `gmpy2` (fast bignum / `gcd` / `isqrt` / `is_prime`), `cryptography` (PEM/DER/SPKI/X.509 parsing), `pytest` + `psutil` (benchmark timing/memory). `sympy.ntheory` only as an independent *oracle* to validate our own ECM/GCD outputs in tests — not as the shipped implementation (implementing ECM ourselves is part of the contribution). Rust is a viable alternative (matches `RSAPubKeyHealth`) but Python is faster to a demonstrable, examinable MVP.

## 7. Reproducible benchmark methodology

**Synthetic corpus generator** (fixed RNG seeds; emits keys + a sealed ground-truth manifest):

| Class | Injected defect | Expected detector |
|---|---|---|
| `healthy` | good CSPRNG, balanced primes, `e=65537`, sizes 1024/2048/3072 | none (true negatives) |
| `shared_prime` | inject one common `p` across a family of `k` keys | batch GCD |
| `close_prime` | choose `q` near `p`, controlled `|p−q|` sweep | Fermat |
| `small_factor` | `n = small_prime · large_prime` (unbalanced) | trial division / ECM |
| `unbalanced` | `p` ~ 128–256 bits, `q` large | ECM (budget study) |
| `small_d` | pick small `d`, derive `e` | Wiener |
| `roca` *(optional)* | structured primes | ROCA fingerprint |

**Metrics:** per-detector precision / recall / F1; detection rate by defect class and modulus size; **false-positive rate on `healthy`** (target ~0); runtime and peak memory per detector; **ECM marginal yield** vs `(B₁,B₂,curves,time)`; batch-GCD scaling vs `N`.

**Reproducibility contract:** pinned dependency versions, fixed seeds, a `manifest.json` describing every key's class and ground truth, and a single command that regenerates the corpus and reproduces every reported number. The harness is the only place private factors and labels exist.

## 8. Implementation roadmap (phased; MVP first)

- **Phase 0 — Foundations.** Repo hygiene, licence, `THREAT_MODEL.md` + ethics/scope, this plan. Env + pinned deps.
- **Phase 1 — Deterministic MVP.** Parser (PEM/DER/SPKI) → metadata checks → trial division → Fermat → Wiener → JSON report → unit tests. Fast, no randomness. *Exit:* audits a single key end-to-end with a clean report.
- **Phase 2 — Benchmark.** Corpus generator + ground-truth manifest + evaluator computing §7 metrics. *Exit:* precision/recall table reproduced from one command.
- **Phase 3 — Batch GCD.** Product-tree/remainder-tree implementation over the corpus; scaling study vs naïve pairwise. *Exit:* recovers injected shared primes; `O(N log²N)` curve.
- **Phase 4 — Bounded ECM.** Stage-1 (+ optional stage-2), budget controls, marginal-yield study (RQ2). *Exit:* recovers unbalanced factors within budget; documented "when not to run".
- **Phase 5 — Fusion & reporting.** Calibrated risk scorer (RQ3), failure-mode attribution, operator vs forensic report split with structural redaction.
- **Phase 6 — Domain + demo + write-up.** IEC 62351 / NERC CIP mapping, remediation guidance, reproducible demo, final report.

**Dependency order:** 0 → 1 → 2 → {3, 4 in parallel} → 5 → 6. HTTP/UI layer (the `image.png` service + dashboard) is deferred to the end (to be built later in a separate UI pass). *Done: `rsashield serve` (`src/server.rs`, `web/`) now covers that feature surface; see the README.*
